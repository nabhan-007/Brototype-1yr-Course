Phase 1: Foundation

Database Theory
An organized collection of structured data. Apps need DBs for persistence (data survives restart), retrieval (query by any field), and scaling (handle millions of users).

SQL vs NoSQL Theory

SQLNoSQL
Tables, rows, columnsCollections, documents, fields
Fixed schema (ALTER required)Dynamic schema (different fields per doc)
Vertical scaling (bigger server)Horizontal scaling (more servers)
ACID compliant by defaultBASE (eventual consistency)
MySQL, PostgreSQL, SQLiteMongoDB, Redis, Cassandra, Neo4j

Vertical vs Horizontal Scaling Theory
Vertical = buy a bigger machine (more RAM/CPU). Has a ceiling.
Horizontal = add more cheap machines. No ceiling, but needs software support (sharding).

Why MongoDB? Theory
Document-oriented (JSON-like data), schema-flexible, horizontal scaling via sharding, rich query language + indexing, large ecosystem.

ACID vs BASE Theory

ACID (SQL)BASE (NoSQL)
Atomicity — all or nothingBasically Available
Consistency — data always validSoft state — may change over time
Isolation — concurrent txns don't interfereEventual consistency — will converge
Durability — committed txns survive crashes

CAP Theorem Theory
You can pick only 2 of 3:

  • Consistency — every read gets the latest write
  • Availability — every request gets a response (even if stale)
  • Partition Tolerance — system works despite network failures

MongoDB chooses CP (Consistency + Partition Tolerance). During a network partition, MongoDB stops accepting writes on one side to maintain consistency.

Transactions in MongoDB Theory
Multi-document ACID transactions supported since v4.0. Use when you need atomic updates across multiple documents/collections. Don't overuse — they add overhead. Prefer embedded documents for simple atomic operations.

Phase 4: Architecture

Document Architecture
A single record — JSON-like key-value pairs. Stored in BSON internally.

Collection Architecture
A group of documents (analogous to a table in SQL). Collections do not enforce a schema.

Database → Collection → Document → Field Architecture

ObjectId Architecture
Auto-generated _id field. 12 bytes:

BytesContent
4Timestamp (seconds since Unix epoch)
5Machine + Process ID
3Counter (incrementing)

JSON vs BSON Architecture
JSON = human-readable text. BSON = binary representation, faster to parse, supports more types (Date, ObjectId, Binary, Decimal128, etc.). MongoDB stores data as BSON internally.

WiredTiger Architecture
The default storage engine. Features: document-level locking, compression, journaling for crash recovery.

Capped Collections Architecture
Fixed-size collections that auto-remove oldest documents when full. Useful for logs, messages.

TTL Indexes Architecture
Index with expireAfterSeconds. MongoDB auto-deletes documents after specified time. Useful for session data, temporary records.

GridFS Architecture
Store files > 16 MB by splitting into chunks (default 255 KB each). Two collections: fs.files (metadata) and fs.chunks (binary).

Replica Set Architecture

  • Primary — accepts all writes, replicates to secondaries
  • Secondary — read-only copies; can become primary on failover
  • Arbiter — votes in elections but stores no data (lightweight)
  • Failover — if primary goes down, secondaries elect a new primary automatically

Sharding Architecture

  • Shard — a server holding a subset of data
  • Shard Key — the field MongoDB uses to distribute documents across shards (choose high cardinality, evenly distributed)
  • mongos — router that directs queries to the right shard
  • Shard when data exceeds a single server's capacity

Phase 5: CRUD Operations

Insert Practical

db.users.insertOne({ name: "Alice", age: 30 })
db.users.insertMany([
  { name: "Bob", age: 25 },
  { name: "Charlie", age: 35 }
])

Read (Query) Practical

db.users.findOne({ name: "Alice" })
db.users.find({ age: { $gt: 25 } })          // age > 25
db.users.find({}, { name: 1, _id: 0 })        // projection (only name)
db.users.find().limit(5).sort({ age: -1 })     // pagination + sort

Query Operators Practical

OperatorMeaningExample

$ltLess than{ age: { $lt: 30 } }
$gte / $lteGreater/less or equal{ age: { $gte: 18 } }

$neNot equal{ status: { $ne: "deleted" } }

Update Practical

db.users.updateOne(
  { name: "Alice" },
  { $set: { age: 31 } }
)
db.users.updateMany(
  { age: { $lt: 30 } },
  { $inc: { age: 1 } }     // increment by 1
)
db.users.replaceOne(
  { name: "Bob" },
  { name: "Bob", age: 26, city: "NYC" }  // replaces entire doc
)

Update Operators Practical

OperatorEffect

$unsetRemove a field

Upsert Practical
Update if exists, insert if not:

db.users.updateOne(
  { name: "Dave" },
  { $set: { age: 28 } },
  { upsert: true }
)

Delete Practical

db.users.deleteOne({ name: "Charlie" })
db.users.deleteMany({ age: { $lt: 20 } })
db.users.findOneAndDelete({ name: "Bob" })   // delete & return doc

Bulk Writes Practical

db.users.bulkWrite([
  { insertOne: { document: { name: "Eve", age: 22 } } },
  { updateOne: { filter: { name: "Alice" }, update: { $set: { age: 32 } } } },
  { deleteOne: { filter: { name: "Bob" } } }
])

Phase 6: Aggregation Framework

Pipeline concept Practical
Documents pass through stages sequentially. Each stage transforms data and passes it to the next.

db.orders.aggregate([
  { $match: { status: "shipped" } },      // filter
  { $group: { _id: "$product", total: { $sum: "$quantity" } } },  // group
  { $sort: { total: -1 } },                // sort descending
  { $limit: 5 }                            // top 5
])

Key Stages Practical

$matchFilter documentsWHERE
$groupGroup by field + computeGROUP BY
$sortReorder documentsORDER BY
$projectReshape (select/compute fields)SELECT
$limit / $skipPaginationLIMIT / OFFSET
$unwindFlatten array into individual docs—
$lookupJoin with another collectionJOIN
$addFieldsAdd computed fields—

Accumulators (inside $group) Practical

AccumulatorWhat it does

$min / $maxMinimum / Maximum
$first / $lastFirst / Last in group

$lookup example Practical

db.orders.aggregate([
  {
    $lookup: {
      from: "customers",
      localField: "customerId",
      foreignField: "_id",
      as: "customer"
    }
  }
])

Phase 7: Schema Design & Indexes

Dynamic Schema Architecture
Documents in the same collection can have different fields. No ALTER TABLE needed.

Embedding vs Referencing Architecture

EmbeddingReferencing
HowNest related data inside the docStore an ID linking to another doc
Use whenData accessed together, 1-to-few1-to-many, many-to-many, data grows independently
ProsSingle query, atomic updatesNo duplication, data stays manageable
ConsDoc size limit (16 MB), duplicationRequires joins ($lookup), multiple queries

Indexes Practical
Speed up reads. Without index → COLLSCAN (scans every doc). With index → IXSCAN (jumps to data).

db.users.createIndex({ name: 1 })              // single-field asc
db.users.createIndex({ age: -1, name: 1 })     // compound (age desc, name asc)
db.users.createIndex({ description: "text" })  // full-text search
db.users.createIndex({ location: "2dsphere" }) // geospatial

Index Types Practical

TypeUse
Single-fieldQuery on one field
CompoundQuery on multiple fields
TextFull-text search ($text)
Geospatial (2dsphere)Location queries ($near)
TTLAuto-delete after time

Covered Query Architecture
A query answered entirely from the index — no documents need to be read. Check with db.users.find(...).explain().

explain() Practical

db.users.find({ age: { $gt: 25 } }).explain("executionStats")

Index Best Practices Architecture

  • Index frequently-queried fields
  • Don't over-index (slows writes)
  • Use explain() to verify
  • Compound indexes support queries with multiple fields
  • Order matters in compound indexes (equality → sort → range)
